2. INTERNAL VELOCITY VS REAL ROBLOX VELOCITY
============================================================

The game has its own movement velocity in DataRegistry:

    DataRegistry["Velocity"]

This is NOT numerically the same as:

    HumanoidRootPart.AssemblyLinearVelocity

Confirmed runtime scale:

    Movement.Update()
        -> calculates Speed from internal Velocity
        -> internal horizontal velocity is roughly real horizontal speed * 90

The recovered movement code contains the relationship:

    Speed = Velocity.Magnitude / 90

Therefore:

    real speed ~= internal horizontal velocity magnitude / 90
    internal velocity ~= real horizontal speed * 90

Example:

    real speed ~= 50
    internal velocity ~= 4500

Observed internal values in air movement were several thousand while
AssemblyLinearVelocity was much smaller.

Do not mix these two velocity representations when calculating movement.

3. EXACT JUMP SPEED LOGIC
============================================================

The discovered Jump() function contains:

    local Speed = v3.Speed

    local v5 =
        v3.JumpSpeedMultiplier *
        v_u_1.Character.HumanoidRootPart.CFrame.lookVector:Dot(Velocity.unit) ^ 2

    local magnitude = Velocity.magnitude

    if magnitude < Sprint * Speed * v5 then

        local v6 = magnitude * v3.JumpSpeedMultiplier
        local v7 = Sprint * Speed * v5
        local v8 = math.min(v6, v7)

        v_u_1.DataRegistry:Set(
            "Velocity",
            (v_u_1.DataRegistry:Get("Velocity") * Vector3.new(1, 0, 1)).unit * v8
        )
    end

So the jump-time horizontal speed target is:

    targetCap =
        Sprint
        * Speed
        * JumpSpeedMultiplier
        * (HumanoidRootPart.lookVector · Velocity.unit)^2

and the rewritten horizontal magnitude is:

    min(
        |Velocity| * JumpSpeedMultiplier,
        targetCap
    )

The direction is based on the existing DataRegistry Velocity after removing Y.


============================================================
4. WHY LOOKING DOWN REDUCES JUMP SPEED
============================================================

This is directly confirmed by the Jump() source.

The relevant factor is:

    (HumanoidRootPart.lookVector · Velocity.unit)^2

For approximately horizontal Velocity aligned with character facing:

    dot ~= cos(pitch)

therefore:

    dot^2 ~= cos(pitch)^2

Useful mathematical reference:

    0°  -> 1.000
    30° -> 0.750
    45° -> 0.500
    60° -> 0.250
    75° -> 0.067
    90° -> 0.000

Actual runtime values depend on the full 3D Velocity direction and relative yaw.

Important:

    JumpHeight is NOT the cause of this horizontal speed reduction.

The reduction comes from the HRP lookVector / Velocity dot product.


============================================================
5. JUMP FLOW
============================================================

Recovered Jump() flow, at the confirmed level:

    1. Reject if Downed.
    2. Reject while carrying a nonzero carried state.
    3. If MoveStats.Speed == 0, do not perform the speed adjustment.
    4. Read Velocity, Sprint and MoveStats.
    5. Calculate HRP lookVector · Velocity.unit.
    6. Square that dot product and multiply by JumpSpeedMultiplier.
    7. Calculate the jump-time horizontal speed cap.
    8. Rewrite horizontal Velocity if current magnitude is below the cap.
    9. Set Humanoid.JumpHeight.
   10. Set Humanoid state to Jumping.
   11. Wallrun jumps have additional wallrun-specific velocity/vertical handling.

============================================================
13. LOOKY IS CALCULATED FROM CAMERA PITCH
============================================================

The Movement.Terms entry for LookY has:

    Term = "LookY"
    DisabledValue = 0
    FunctionActiveOnServer = false

Its CalculateFunction is:

    local Y2 = v_u_3:GetCFrame().lookVector.Y
    local v20 = math.asin(Y2) * 40 + 0.5
    return math.floor(v20) / 40

So the game's LookY value is a quantized pitch angle in radians.

It is NOT:

    sin(pitch)

It is effectively:

    LookY =
        floor(
            asin(CameraCFrame.lookVector.Y) * 40 + 0.5
        ) / 40

Quantization step:

    1 / 40 radian ~= 0.025 rad


============================================================
14. WHY DIRECTLY FORCING DATREGISTRY["LOOKY"] DID NOT WORK
============================================================

This was tested and the reason was recovered.

Character.Update() does, for local characters:

    DataRegistry:Set("LookCFrame", CameraService:GetCFrame())

Then, when movement is active:

    Movement:UpdateTerms(...)

The Movement.Terms system recalculates LookY from the live camera CFrame.

Therefore a later direct assignment such as:

    DataRegistry:Set("LookY", target)

can be overwritten by Movement.UpdateTerms() before UpdateCycle() sends the
actual term.

This was observed in diagnostics: a manually forced target could exist briefly,
but the outgoing value later became the native camera-derived value.

Conclusion:

    Do NOT treat a RenderStep write to DataRegistry["LookY"] as the reliable
    source of the game's outgoing LookY value.

15. CONFIRMED SOLUTION POINT FOR RAGE LOOK
============================================================

The correct integration point is the native Movement.Terms CalculateFunction.

Working test:

    1. Find:
       ReplicatedStorage.Objects.Game.Character.Client.Movement.Terms

    2. require() the module.

    3. Find the entry where:
           entry.Term == "LookY"

    4. Save:
           entry.CalculateFunction

    5. Replace only the CalculateFunction with one returning the target
       quantized LookY.

For a target physical pitch of about -70 degrees:

    RAGE_LOOK_PITCH = -math.rad(70)

The game's own quantization gives:

    RAGE_LOOK_Y =
        math.floor(RAGE_LOOK_PITCH * 40 + 0.5) / 40

which equals:

    -1.225

A standalone runtime test using this exact Terms replacement produced:

    DataRegistry["LookY"] = -1.225
    ToSend["LookY"]         = -1.225

This is important because it proves the value reached the normal DataRegistry
send queue rather than being only a temporary local override.

This is the confirmed mechanism used by the DeadEye Rage Look implementation.

16. RAGE LOOK PHYSICAL CFRAME HOOK
============================================================

The game physics need to believe the character is looking down, but the actual
camera should remain visually unchanged.

The confirmed local technique is:

    intercept DataRegistry.Get()

and only for:

    key == "LookCFrame"

return a fake CFrame with:

    same position
    same horizontal/yaw orientation
    target pitch, approximately -70 degrees

Do NOT modify:

    HumanoidRootPart.CFrame
    workspace.CurrentCamera.CFrame
    RootPartOrienter
    Head.Transform
    Head.C0

The purpose of this hook is specifically to affect code that reads:

    DataRegistry:Get("LookCFrame")

for movement/physics logic.

Most importantly, the Jump() slowdown reads:

    HumanoidRootPart.CFrame.lookVector

so the effect of the physical-look solution is to make the character's actual
movement/physics look downward through the native character-orientation/data
path without visually forcing the local camera downward.

The currently used DeadEye implementation keeps the LookCFrame hook separate
from the LookY replication path.

24. ACCELERATE HELPER — EXACT MATHEMATICS
============================================================

Path:

    ReplicatedStorage.Objects.Game.Character.Client.Movement
    .MoveFunction.Functions.Helpers

Function:

    Accelerate

Recovered core logic:

    if special == true then
        acceleration *= 0.4
        wishSpeed *= 1.3
    end

    currentSpeed = currentVelocity:Dot(wishDirection)

    addSpeed = wishSpeed - currentSpeed

    if addSpeed <= 0 then
        return currentVelocity
    end

    accelSpeed = acceleration * deltaTime * wishSpeed

    if addSpeed >= accelSpeed then
        addSpeed = accelSpeed
    end

    return currentVelocity + addSpeed * wishDirection

This internal helper formula is confirmed.

The helper structure is therefore:

    currentSpeed = V · W
    addSpeed     = wishSpeed - currentSpeed

    if addSpeed <= 0:
        no acceleration

    acceleration cap:
        acceleration * dt * wishSpeed

    actual added velocity:
        wishDirection * min(addSpeed, accelSpeed)

============================================================
29. APPLYFRICTION — EXACT SOURCE LOGIC
============================================================

The helper does:

    Velocity =
        DataRegistry:Get("Velocity")

    magnitude =
        Velocity.magnitude

    RunDeaccel =
        MoveStats.RunDeaccel

    Friction =
        MoveStats.Friction

If Swimming:

    RunDeaccel *= 0.6
    Friction   *= 0.6

Then:

    if magnitude < RunDeaccel then
        v12 = RunDeaccel
    else
        v12 = magnitude
    end

Equivalent:

    v12 = max(RunDeaccel, magnitude)

Then:

    v13 =
        magnitude
        - v12 * Friction * dt * p11

Clamp:

    v14 = max(v13, 0)

Then, if magnitude > 0:

    v14 = v14 / magnitude

Finally:

    return Velocity * v14

For nonzero velocity, the subtracted amount before clamping is:

    loss =
        max(RunDeaccel, magnitude)
        * Friction
        * dt
        * p11


============================================================
30. APPLYFRICTION NORMAL RUN CASE
============================================================

Normal Run:

    p11 = 1

Non-swimming:

    RunDeaccel = unchanged
    Friction   = unchanged

Therefore:

    loss =
        max(RunDeaccel, |Velocity|)
        * Friction
        * dt

At high internal speeds where:

    |Velocity| > RunDeaccel

the formula simplifies to:

    newMagnitude / oldMagnitude =
        1 - Friction * dt

With:

    Friction = 5

and a tested:

    dt ~= 0.0083

the multiplier is approximately:

    1 - 5 * 0.0083
    ~= 0.9585

For another tested:

    dt = 0.007786

the multiplier is:

    1 - 5 * 0.007786
    = 0.96107

These are direct consequences of the recovered source formula.

31. APPLYFRICTION AND THE OBSERVED LANDING LOSS
============================================================

Recovered Run source establishes that normal grounded movement executes:

    ApplyFriction(...)
        ->
    Accelerate(...)
        ->
    WallImpact(...)

The complete ApplyFriction source establishes exactly how the first operation
reduces DataRegistry["Velocity"].

At high internal speeds:

    |Velocity| > RunDeaccel

so:

    friction multiplier =
        1 - 5 * dt

and the first Run tick can remove several percent of internal speed.

Example at:

    real horizontal speed ~= 50
    internal speed ~= 4500
    dt = 0.007786

friction-only reduction:

    4500 * (1 - 0.96107)
        ~= 175.2 internal

converted through the confirmed /90 scale:

    175.2 / 90
        ~= 1.95 real speed

This is a numerical match to the previously observed approximately 2-unit
landing reduction.

Important:

The file now treats the source-level ApplyFriction reduction as confirmed.
The exact complete final landing delta is still the result of the whole Run
pipeline because Accelerate and WallImpact execute afterward.

Therefore:

    ApplyFriction = confirmed direct velocity-reducing operation

while:

    final landing speed change =
        interaction of ApplyFriction + Accelerate + WallImpact + other Run logic


============================================================
32. APPLYFRICTION MODIFICATION LEVER
============================================================

The recovered helper multiplies the friction subtraction by:

    p11

Therefore:

    p11 = 1
        -> normal friction

    p11 = 0
        -> no friction subtraction for that call

    p11 = smaller positive value
        -> proportionally reduced friction

Normal Run uses:

    p11 = 1

Air and Slide also use ApplyFriction, with different call contexts.

Known call:

    Slide:
        ApplyFriction(..., 0.1)

Known Air-side use:

    ApplyFriction(..., 1)
    under its own branch conditions

Therefore globally replacing ApplyFriction is not equivalent to modifying only
ground landing behavior.

33. MOVEMENT STATE TRANSITION — CONFIRMED
============================================================

Movement.SetState(newState) was recovered.

When state changes, it:

    1. gets current MoveStats;
    2. ends previous state;
    3. starts new state;
    4. reads new StateInfo;

52. 2026-10-05 — DERIVED PURE A/D + CAMERA STRAFE LAW
============================================================

This section is mathematical derivation from the confirmed Air() and
Accelerate() source.

It is not an engine-side hypothesis.

The source-confirmed pure A/D conditions are:

    WishDirection = camera-relative lateral direction
    WishSpeed     = 182
    Acceleration  = 182
    AirControl    = skipped because MoveDirection.Z == 0

Let:

    V = current horizontal Velocity
    W = unit WishDirection from A/D
    S = 182
    theta = angle between V and W

Then:

    V · W = |V| * cos(theta)

Accelerate requests:

    addSpeed = S - |V| * cos(theta)

and caps it by:

    K = S * dt * S

So the actual A/D velocity update is:

    a = min(S - |V| cos(theta), K)

provided:

    S - |V| cos(theta) > 0

and:

    V_new = V + aW


-------------------------------------------------------------
52.1 EXACT SPEED MAXIMUM — W PERPENDICULAR TO VELOCITY
-------------------------------------------------------------

In the uncapped branch:

    a = S - V cos(theta)

where:

    V = |Velocity|

Then:

    |V_new|^2
        = V^2 + a^2 + 2Va cos(theta)

Substituting:

    |V_new|^2
        = V^2 + S^2 - V^2 cos^2(theta)

Therefore:

    |V_new|^2
        = V^2 + S^2 - V^2 cos^2(theta)

This is maximized when:

    cos(theta) = 0

therefore:

    theta = 90 degrees

So the exact maximum-speed condition for pure A/D is:

    WishDirection PERPENDICULAR to current horizontal Velocity.


-------------------------------------------------------------
52.2 CAMERA GEOMETRY FOR THE MAXIMUM
-------------------------------------------------------------

For normal horizontal camera orientation:

    CameraRight
        is perpendicular to
    CameraLook

Pure A/D uses:

    D -> +CameraRight
    A -> -CameraRight

Therefore the maximum-speed condition is achieved when the horizontal
CameraLook direction is parallel or antiparallel to the current horizontal
Velocity.

A simple practical orientation is:

    CameraLook ~= Velocity direction

Then:

    D -> perpendicular rightward WishDirection
    A -> perpendicular leftward WishDirection

The held A/D key selects which side of Velocity the acceleration is applied.


-------------------------------------------------------------
52.3 MAXIMUM SPEED GAIN PER MOVEMENT TICK
-------------------------------------------------------------

At the optimal condition:

    V · W = 0

therefore:

    addSpeed = S = 182

as long as the acceleration cap does not bind.

The new speed is:

    V_new = sqrt(V^2 + S^2)

so:

    DeltaSpeed =
        sqrt(V^2 + 182^2) - V

Because DataRegistry velocity is approximately real speed * 90:

    DeltaRealSpeed =
        (sqrt(V^2 + 182^2) - V) / 90


-------------------------------------------------------------
52.4 EXAMPLE AT INTERNAL SPEED 4500
-------------------------------------------------------------

Using:

    V = 4500
    S = 182

gives:

    DeltaInternalSpeed
        ~= 3.67894

and:

    DeltaRealSpeed
        ~= 0.04088

per movement step at the exact perpendicular condition.

The corresponding Velocity heading change is:

    delta =
        atan2(182, 4500)

        ~= 2.316 degrees

So near internal speed 4500:

    optimal Velocity turn per movement step
        ~= 2.316 degrees


-------------------------------------------------------------
52.5 CAMERA SHOULD TRACK VELOCITY, NOT USE A FIXED TURN RATE
-------------------------------------------------------------

After the optimal update:

    V_new = V + 182 * W

with:

    W perpendicular to V

the new Velocity itself has rotated by:

    delta =
        atan2(182, V)

Therefore, to keep the next A/D WishDirection perpendicular to the NEW
Velocity, the camera's horizontal look direction must rotate by the same
world-yaw amount as the Velocity heading.

So the adaptive rule is:

    each movement step:
        1. read current horizontal Velocity heading;
        2. point CameraLook along that heading;
        3. hold A or D;
        4. after the resulting Velocity update, recompute;
        5. rotate CameraLook to the new Velocity heading.

The required camera tracking angle is therefore not constant.

It decreases automatically as speed increases:

    delta_camera ~= atan2(182, |Velocity|)


-------------------------------------------------------------
52.6 GENERAL CAMERA/VElocity ERROR EQUATION
-------------------------------------------------------------

Define:

    e = VelocityYaw - CameraYaw

For normal horizontal camera orientation and pure A/D:

    D:
        WishDirection angle = CameraYaw + 90 degrees

    A:
        WishDirection angle = CameraYaw - 90 degrees

For D, the dot term can be written as:

    Velocity · WishDirection
        = V * sin(e)

For A, the sign is reversed:

    Velocity · WishDirection
        = -V * sin(e)

Thus camera yaw error changes the Accelerate dot term directly.

For D:

    addSpeed =
        182 - V * sin(e)

subject to the normal positive test and acceleration cap.

For A:

    addSpeed =
        182 + V * sin(e)

with the same cap conditions.

This explains why changing camera yaw while holding A/D changes the amount of
acceleration even though the pressed key itself has not changed.


-------------------------------------------------------------
52.7 CAMERA TURN RATE AND VELOCITY TURN RATE
-------------------------------------------------------------

Let:

    omega = camera yaw change during one movement step
    delta  = resulting Velocity yaw change

Then the next camera/Velocity error is:

    e_new =
        e + delta - omega

(with the sign convention e = VelocityYaw - CameraYaw).

Therefore:

    omega = delta

keeps the yaw error unchanged.

At the optimal condition:

    e = 0

the exact target is:

    omega_target =
        atan2(182, |Velocity|)

so that the camera continues tracking the changing Velocity direction.


-------------------------------------------------------------
52.8 ACCELERATION CAP BOUNDARY
-------------------------------------------------------------

The normal A/D acceleration cap is:

    K = 182 * dt * 182

The uncapped request is:

    182 - V cos(theta)

The cap starts binding when:

    182 - V cos(theta) > K

or:

    cos(theta) < (182 - K) / V

For dt >= 1/182 ~= 0.005495 seconds:

    K >= 182

so at the optimal perpendicular condition:

    theta = 90 degrees

the request:

    addSpeed = 182

does not exceed the cap.

Typical tested movement dt values around 0.008 therefore leave the optimal
perpendicular A/D case uncapped.


-------------------------------------------------------------
52.9 GLOBAL OPTIMUM ALSO HOLDS IN THE CAPPED BRANCH
-------------------------------------------------------------

When the cap is active:

    a = K

and:

    |V_new|^2 = V^2 + K^2 + 2VK cos(theta)

Within the capped region this is largest at the boundary.
