2. EXACT JUMP SPEED LOGIC
============================================================

The discovered Jump() function contains:

local Speed = v3.Speed

local v5 =
    v3.JumpSpeedMultiplier *
    v_u_1.Character.HumanoidRootPart.CFrame.lookVector:Dot(Velocity.unit) ^ 2

local magnitude = Velocity.magnitude

if magnitude < Sprint * Speed * v5 then

    local v6 = magnitude * v3.JumpSpeedMultiplier
    local v7 = Sprint * Speed * v5
    local v8 = math.min(v6, v7)

    v_u_1.DataRegistry:Set(
        "Velocity",
        (v_u_1.DataRegistry:Get("Velocity") * Vector3.new(1, 0, 1)).unit * v8
    )
end

Thus the jump-time horizontal velocity rewrite is effectively:

targetCap =
    Sprint
    * Speed
    * JumpSpeedMultiplier
    * (HumanoidRootPart.lookVector · Velocity.unit)^2

newHorizontalSpeed =
    min(
        |Velocity| * JumpSpeedMultiplier,
        targetCap
    )

The direction is taken from the existing Velocity after removing Y.


============================================================
3. LOOKING DOWN REDUCES JUMP SPEED
============================================================

The reduction is NOT caused by JumpHeight.

It comes from:

(HumanoidRootPart.lookVector · Velocity.unit)^2

If velocity is approximately horizontal and aligned with facing direction:

dot ~= cos(pitch)

so:

dot^2 ~= cos(pitch)^2

Examples:
0°  -> 1.000
30° -> 0.750
45° -> 0.500
60° -> 0.250
75° -> 0.067
90° -> 0.000

Actual values depend on the full 3D Velocity.unit vector and relative yaw.


============================================================
4. JUMP FLOW
============================================================

Jump() approximately:

1. Reject if Downed.
2. Reject while carrying a nonzero carried state.
3. Ignore movement speed adjustment if MoveStats.Speed == 0.
4. Read Velocity, Sprint and MoveStats.
5. Calculate the lookVector/Velocity dot-squared factor.
6. Calculate the jump-time horizontal velocity cap.
7. Rewrite horizontal Velocity only when current magnitude is below that cap.
8. Set Humanoid.JumpHeight.
9. Change Humanoid state to Jumping.
10. Wallrun jumps have additional velocity and vertical handling.

17. IMPORTANT PHYSICS SUMMARY
============================================================

Current confirmed model:

GROUND / GENERAL MOVEMENT:
- friction/deceleration acts through ApplyFriction
- acceleration acts through Accelerate
- Speed / Sprint / SprintCap participate in movement speed limits

AIR MOVEMENT:
- AirAcceleration = 1
- AirStrafeAcceleration = 182
- Accelerate applies capped acceleration based on:
      addSpeed = wishSpeed - currentVelocity·wishDirection
      accelSpeed = acceleration * dt * wishSpeed
- AirControl adds a separate directional-air-control operation.

JUMP:
- JumpSpeedMultiplier = 1.45
- Jump speed depends on:
      (HumanoidRootPart.lookVector · Velocity.unit)^2
- Sprint * Speed also forms the jump speed cap.
- Looking down can therefore reduce the preserved horizontal speed.

CAMERA:
- Active path is ClassicCamera.
- Programmatic rotation is possible through:
      CameraInput.getRotation upvalue[4].Movement
- This is preferable to directly forcing CurrentCamera.CFrame when trying to
  participate in the game's native camera pipeline.

19.3 ACCELERATE CALL ARGUMENT MAPPING — CONFIRMED
------------------------------------------------------------

Runtime raw argument tracing established the actual call layout:

    Accelerate(
        self,          -- arg 1
        velocity,      -- arg 2
        wishDirection, -- arg 3
        acceleration,  -- arg 4
        wishSpeed,     -- arg 5
        deltaTime,     -- arg 6
        special        -- arg 7
    )

This mapping is confirmed by the observed argument types and returned values.

For normal air calls:
    acceleration = 182
    wishSpeed    = 182
    deltaTime    ~= 0.008

The observed return delta matches an additional factor of 10:

    accelSpeed = acceleration * 10 * deltaTime * wishSpeed

Thus the effective confirmed helper behavior in the tested air context is:

    if special == true then
        acceleration = acceleration * 0.4
        wishSpeed = wishSpeed * 1.3
    end

    currentSpeed = velocity:Dot(wishDirection)
    addSpeed = wishSpeed - currentSpeed

    if addSpeed <= 0 then
        return velocity
    end

    accelSpeed = acceleration * 10 * deltaTime * wishSpeed

    if addSpeed >= accelSpeed then
        addSpeed = accelSpeed
    end

    return velocity + addSpeed * wishDirection

IMPORTANT:
The factor 10 is confirmed from runtime return-value matching for the tested
air calls. It was not directly visible as a literal in the earlier helper
decompile, so retain this distinction.

The special=true behavior (0.4 acceleration / 1.3 wishSpeed) is confirmed from
the helper decompile, but the line-109 condition that sets arg 7 to true is
still not recovered.

19.4 AIRCONTROL ARGUMENT MAPPING — CONFIRMED
------------------------------------------------------------

Runtime tracing of AirControl established:

    arg 1 = self/table
    arg 2 = vector whose Z is tested
    arg 3 = number (observed around 1620 in the tested calls)
    arg 4 = Vector3 lateral/right direction (often ±1,0,0 in world space)
    arg 5 = current Velocity
    arg 6 = deltaTime

This corresponds to the helper's internal roles:

    v1 = arg 2
    v3 = arg 3
    v5 = arg 4
    v2 = arg 5
    v6 = arg 6

The helper is:

    local Z = v1.Z

    if math.abs(Z) < 0.001 or math.abs(v3) < 0.001 then
        return v2
    end

    local magnitude = v2.magnitude
    local unit = v2.unit
    local dot = unit:Dot(v5)

    local unused = 32 * (1 * dot * dot * v6)

    return unit * Vector3.new(magnitude, 0, magnitude)

In the observed calls, the returned value matched arg 5/current Velocity
exactly. The 32 * dot^2 * dt intermediate is assigned to an unused local in
the available decompile and was not observed changing the returned vector.

Therefore:
- do NOT currently treat 1620 as a proven "meaning" such as Speed*1.08;
- do NOT treat AirControl as the direct source of the observed horizontal
  air-strafe rotation;
- the exact intended role of the unused intermediate remains unresolved.

19.5 WISHDIR — CONTROLLED INPUT TESTS
------------------------------------------------------------

Multiple controlled camera/input tests established the following behavior.

W:
    WishDir = CameraLook

D:
    WishDir = CameraRight

A:
    WishDir = -CameraRight

W+D:
    WishDir = CameraRight

W+A:
    WishDir = -CameraRight

During long smooth camera rotation, WishDir continued to track the corresponding
CameraRight / -CameraRight vector exactly (dot ~= 1.0).

Humanoid.MoveDirection remained normal diagonal input for W+A/W+D, so the air
WishDir is NOT simply Humanoid.MoveDirection.

Current best-supported direction-selection model:

    if D/right-lateral input > 0 then
        WishDir = CameraRight
    elseif A/left-lateral input < 0 then
        WishDir = -CameraRight
    else
        WishDir = CameraLook
    end

This is behaviorally strongly confirmed, but the exact line-109 source branch
that produces it is still NOT directly recovered.

This means lateral input takes priority over W in the tested air-strafe path.

16. DERIVED OPTIMAL AIR-STRAFE STEERING
=============================================================

Controlled camera tests in file "s" established:

FIXED:
    camera turn = 0 deg/frame
    horizontal speed change = 0

SLOW:
    camera turn ~= 0.33 deg/frame
    HSpeed increase ~= 0.97 registry units/call

MEDIUM:
    camera turn ~= 0.66 deg/frame
    HSpeed increase ~= 1.79 registry units/call

FAST:
    camera turn ~= 0.99 deg/frame
    HSpeed increase ~= 2.45 registry units/call

Accelerate() itself is confirmed to perform:

addSpeed = wishSpeed - Velocity:Dot(wishDirection)

if addSpeed <= 0:
    return Velocity

accelSpeed = acceleration * dt * wishSpeed

addSpeed = min(addSpeed, accelSpeed)

Velocity = Velocity + addSpeed * wishDirection


For a fixed current horizontal velocity magnitude V, wish speed W,
and wish direction w, the resulting speed is maximized when:

Velocity · w = 0

Therefore the optimal air-strafe condition is:

WishDirection PERPENDICULAR to current horizontal Velocity.


For W+D:

    WishDirection = CameraRight

CameraRight is perpendicular to CameraLook.

Therefore the optimal W+D steering condition is:

    CameraLook approximately aligned with current horizontal Velocity.

For W+A:

    WishDirection = -CameraRight

The corresponding optimal condition is the opposite camera-side solution.

When the current velocity and wish direction are exactly perpendicular,
and the acceleration cap does not bind, the ideal one-step velocity-angle change
is approximately:

    deltaAngle = atan(WishSpeed / HSpeed)

Using the confirmed active values:

    WishSpeed = 182
    HSpeed ~= 4500 registry units

gives approximately:

    deltaAngle ~= atan(182 / 4500)
               ~= 2.32 degrees per movement/physics step

At dt ~= 1/120:

    ideal camera angular rate ~= 278 deg/s

This is a derived steering target, not yet an experimentally confirmed
engine maximum.

The important control law for the future A->B planner is therefore:

1. Read current horizontal Velocity.
2. Select the desired strafe side (A or D).
3. Keep CameraRight / -CameraRight perpendicular to Velocity.
4. Rotate CameraLook so that it tracks the current Velocity direction.
5. Recompute every movement step because the velocity direction itself changes.
6. Avoid fixed camera turn rates as the primary controller.

This means the future trajectory planner should optimize camera tracking error
relative to Velocity, not simply hold a fixed camera yaw rate.

21.4 NEW IMPORTANT LEAD — APPLYFRICTION NUMERICALLY MATCHES THE OBSERVED LOSS
-------------------------------------------------------------

ApplyFriction is now the strongest concrete explanation for the observed
landing speed drop.

Recovered helper:

    local Velocity = DataRegistry:Get("Velocity")
    local magnitude = Velocity.magnitude

    local RunDeaccel = stats.RunDeaccel
    local Friction = stats.Friction

    local v4
    if magnitude < RunDeaccel then
        v4 = RunDeaccel
    else
        v4 = magnitude
    end

    local newMagnitude =
        magnitude - v4 * Friction * dt * <mode>

    ...
    return Velocity * (newMagnitude / magnitude)

For the observed internal air speeds, magnitude is several thousand
registry units while:

    RunDeaccel = 700

so:

    magnitude > RunDeaccel
    =>
    v4 = magnitude

Therefore, in the normal/non-swimming case, the multiplier simplifies to:

    newMagnitude / magnitude
        =
    1 - Friction * dt

With the confirmed base:

    Friction = 5

the first Run friction tick is approximately:

    multiplier = 1 - 5 * dt

        = 1 - 5 * 0.007786
        = 0.96107

per such Run tick.
